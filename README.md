# FinBridge

Инструмент за счетоводни кантори: банково извлечение вътре, списък с липсващи документи и готов файл за осчетоводяване вън.

## Какво прави

- Акаунти за кантори. Всяка кантора вижда само своите фирми и файлове.
- Импорт на банкови извлечения: CSV, Excel (.xlsx), MT940, XML (camt.053), текстов PDF. Непознат формат се разчита с Claude.
- Качване на фактури (снимки и PDF). Claude ги разчита ред по ред, системата ги свързва с плащането по сума, дата и име.
- Страница за клиента (отваря се от телефона с връзка, без парола):
  - напредък за месеца, срок и приблизително колко ДДС е под въпрос без липсващите документи;
  - снимане или качване на документ към конкретно плащане; обяснение „няма документ“, което счетоводителят приема с един бутон;
  - качване на банковото извлечение, договори и други документи; счетоводителят импортира извлечението с един бутон;
  - въпроси от счетоводителя по конкретно плащане, с отговор от телефона и известие по имейл;
  - история на изпратеното и, по избор за всяка фирма, обобщение на разходите и постъпленията.
- Напомняния: готов текст със списъка и връзката; изпращане по имейл през SMTP. С отметка на фирмата сървърът напомня сам на всеки няколко дни в работно време, докато има липсващи документи за приключен месец.
- Проверки на документите: контролна цифра на ЕИК, необичайна ставка на ДДС, възможен дубликат.
- Контиране: предложение за сметка по вида на доставката; сметката, зададена ръчно, се помни като правило за доставчика и се прилага за следващите му документи. Работен дневник на покупките с разбивка по данъчен кредит.
- Едно плащане за няколко фактури от същия доставчик се засича автоматично, когато сборът съвпада точно.
- Правила за контрагенти, чиито плащания никога не искат документ; раздел „Правила“ за преглед и изтриване.
- Отбелязване на месеца като приключен: спира напомнянията и въпросите към клиента за него.
- Експорт в CSV: документи с плащанията, редове по документи, плащания без документ. Колоните, редът им, разделителят, форматът на датите и кодировката (UTF-8 или Windows-1251) се настройват по шаблона на счетоводната програма.
- Екип: добавяне и премахване на колеги, смяна на парола, забравена парола по имейл.
- Архив на данните на кантората като JSON файл.
- Оригиналните файлове се пазят и се отварят от документа.

## Финансово управление за фирмите

Същото приложение има второ лице за самите фирми. Кантората работи със счетоводната част, а фирмата влиза със собствен вход във финансовата.

- **Разходи с одобрение.** Служителят подава разход от телефона и снима бележката. Одобряващият или собственикът го одобрява или отказва с причина. Одобреният документ отива сам в „Документи“ на счетоводителя.
- **Плащания към доставчици.** Фактури с падеж минават през одобрение и после се отбелязват като платени. Документът стига до счетоводителя веднага.
- **Вземания.** Издадени фактури с падеж, просрочия по давност и отбелязване на получено плащане.
- **Бюджети.** Месечен лимит по категория или по проект, с изпълнение и предупреждение при превишаване.
- **Засичане с банката.** Когато счетоводителят качи извлечението, еднозначните плащания сами затварят вземането, одобрената фактура или разхода с фирмена карта. Съмнителните излизат като предложения за потвърждение с едно натискане. Документът на доставчика стига до счетоводителя вече отнесен към плащането.
- **Напомняне за просрочено вземане.** Готов текст за клиента, който се копира с един бутон.
- **Табло.** Наличност, чакащи одобрение, сума за плащане, прогноза за 8 седмици по падежи и банковите движения от счетоводството.
- **Правила.** Лимит за одобряващия, сума, над която се иска документ, предупреждение за дубликат и бъдеща дата.
- **Роли.** Собственик, одобряващ и служител. Служителят вижда само своите разходи.

Достъп се дава по два начина. Кантората отваря „Редактирай“ на фирмата, после „Отвори финансите“, и създава входове в „Екип и правила“. Фирма без кантора се регистрира сама от входната страница с избор „Фирма“ и може да покани своя счетоводител, който получава счетоводната част за нея.

Модулът не издава карти и не нарежда плащания. Наличността се въвежда ръчно.

## Изисквания

Node.js 22.13 или по-нов. Няма други зависимости и няма `npm install`.

## Стартиране

```
cp .env.example .env        # попълнете стойностите
set -a; . ./.env; set +a
npm start
```

Отворете `http://localhost:8080`, създайте акаунт на кантората и добавете първата фирма.

### С Docker

```
docker build -t finbridge .
docker run -d --name finbridge -p 8080:8080 -v finbridge-data:/data --env-file .env -e DATA_DIR=/data finbridge
```

### На сървър

Сложете приложението зад обратен прокси с HTTPS (Caddy, nginx или облачен балансьор) и задайте `BASE_URL=https://вашият-домейн` и `TRUST_PROXY=true`. Без HTTPS паролите и документите пътуват в открит вид.

Примерен Caddyfile:

```
finbridge.example.bg {
    reverse_proxy 127.0.0.1:8080
    request_body { max_size 20MB }
}
```

## Настройки

| Променлива | За какво е |
| --- | --- |
| `PORT`, `DATA_DIR` | порт и папка за базата и файловете |
| `BASE_URL` | публичен адрес; влиза във връзките за клиентите |
| `TRUST_PROXY` | `true` зад обратен прокси |
| `ALLOW_SIGNUP` | `false` спира регистрацията на нови кантори |
| `ANTHROPIC_API_KEY`, `ANTHROPIC_MODEL` | разчитане с Claude; без ключ документите се въвеждат ръчно |
| `SMTP_HOST`, `SMTP_PORT`, `SMTP_SECURE`, `SMTP_USER`, `SMTP_PASS`, `SMTP_FROM` | изпращане на имейли; без тях текстът се копира ръчно |
| `REMIND_EVERY_DAYS` | през колко дни се повтаря автоматичното напомняне (по подразбиране 3) |

## Администриране

```
node admin.js list
node admin.js set-password <имейл> <нова парола>
node admin.js add-user <имейл на колега от кантората> <нов имейл> <парола>
```

Изпълняват се със същата `DATA_DIR` като сървъра.

## Архивиране

Всичко е в `DATA_DIR`: базата `finbridge.db` (плюс `-wal` и `-shm` файловете) и папката `files`. Архивирайте цялата папка, най-добре при спрян сървър или с `sqlite3 finbridge.db ".backup backup.db"`.

## Тестове

```
npm test             # логика и API (40 + 32 проверки), нужен е само Node
npm run test:e2e     # двата потока в браузър (20 + 8 стъпки); нужни са Playwright и Chrome
```

За `test:e2e` задайте `PLAYWRIGHT=<път до модула playwright>` и `CHROME=<път до Chrome>`, ако не са на стандартните места.

## Какво е проверено и какво не

Проверено с автоматични тестове: регистрация и вход, разделяне на данните между кантори, импорт на всички формати, разчитане и засичане, клиентската връзка и отговорите от нея, ръчни и автоматични имейли, екип и пароли, настройваем експорт, архив, изтриване.

Не е проверено в реална среда и трябва да се пробва след инсталация:

- реално извикване на Claude API (тестовете ползват заместител със същия формат на заявката);
- SMTP през TLS (тестовете ползват некриптирана връзка към локален сървър);
- Docker образът (написан е, но не е билдван);
- извлечения от реални банки (тествано е с примерни файлове).

## Ограничения

- Няма изпращане по Viber, няма Open Banking връзка, няма шаблони за конкретна счетоводна програма (експортът е общ CSV).
- Всички в екипа имат еднакви права; няма плащане на абонамент. Архивът се изтегля, но няма възстановяване от него през интерфейса.
- Частични плащания (една фактура, платена на части) се отбелязват ръчно.
- Следят се само разходите; издадените фактури и вземанията не се засичат.
- Сметките са свободен текст с няколко предложения, няма пълен сметкоплан; дневникът на покупките е работен CSV, не файл във формата на НАП.
- Един процес с SQLite: подходящо за пилот с десетки кантори, не за стотици едновременни потребители.
- Преди работа с реални клиентски данни са нужни политика за поверителност, договор за обработка на данни и редовни архиви.
